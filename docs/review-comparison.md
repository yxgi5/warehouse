## 1. 独立评审（先做，未受第三方影响）

### 1.1 数据库设计

**做得好的（专业级）**

- `containers.parent_id` 自引用建**层级定位树** + `location` 文本：真 WMS「库→架→盒→袋」思路，能拼出完整「在哪」。
- 外键纪律：`PRAGMA foreign_keys=ON`、容器 `ON DELETE RESTRICT`（删容器不 orphan 物品）、子表 `ON DELETE CASCADE`。
- `tags`/`item_tags` 真多对多，旧逗号串一次性迁走；`images` 池 + `sha256` 内容寻址去重 + `item_images` 多对多。
- 迁移框架可重入自愈、`VACUUM INTO` 一致性备份：企业级严谨度。

**缺口 / 风险（按严重度）**

1. **金额用 `REAL` 浮点存（高）** — `items.price REAL`。浮点存钱是经典反模式，3000+ 件 `SUM(price)` 会累积舍入误差，总价值报表不精确。应改 `INTEGER`（分）或十进制字符串。
2. **`purchase_date` 纯 `TEXT` 无校验（中高）** — 格式可能混入 `2026-08-20` / `2026/8/20` 等，无法可靠排序/按年报表。SQLite 无原生 DATE，ISO-8601 `TEXT` 是对的，但缺输入校验，应统一 + 校验。
3. **容器层级无环检测（中高）** — `update_container` 直接写 `parent_id`，无「新父容器不能是自己/子孙」校验，一旦成环树渲染会无限递归/卡死。需向上走祖先链拒绝。
4. **物品/容器两套图片模型（中）** — 物品走「池 + sha256 去重 + 多对多」，容器照片是独立 `container_images`（无去重、一图一记录）。同构需求写了两套 `save/move/delete`，容器照片不能复用、重复落盘。
5. **无审计痕迹（中）** — 无 `movements` 流水（入/出/移的时间戳+原因），也无最基础的 `created_at`/`updated_at`。「我上个月把 X 挪到哪了」答不出。
6. **缺索引（低-中）** — SQLite 外键列不自动建索引：`items.container_id`、`item_tags.tag_id`（复合主键第二列）、`next_item_no` 的 `item_no LIKE 'ITEM_...%'` 均全表扫；`get_filtered_data` 的 `LOWER(列) LIKE` 天然走不了索引，数据再涨会变慢。
7. **死代码/死字段（低）** — `items.tags` 迁空后列仍在；根目录 `containers_tab.py`/`items_tab.py` 与 `ui/` 重复、**全仓 0 处引用**（已核实），纯属误导。

### 1.2 应用设计

**做得好的**

- 分层干净：`db.py → repo.py → ui/ → app.py`，`db`/`repo` 不依赖 streamlit，可直接单测。
- 数据层显式传 `conn`（可测试、无隐藏全局态），物品删除收口唯一入口 `delete_item`。
- 性能意识到位：后台线程备份、孤儿扫描 10 分钟进程级缓存、`df_all_shared` 主查询每 rerun 只查一次。

**缺口 / 风险**

1. **写路径异常不回滚（高）** — `add_item`/`update_item` 是「INSERT → 写标签 → 落图 → commit」串行；落图抛异常时中间已 INSERT 但无 rollback。连接经 `st.cache_resource` 缓存复用，残留未提交事务会带到下次 rerun，可能「database is locked」或脏写。需 try/except rollback（或事务上下文）。
2. **`session_state` 导航状态机脆弱（中高）** — `jump_to_tab`、`detail_*_id`、`edit_*_id`、`add_*_mode`、`tree_scroll_restore`、`nav_origin`、`_fs_sig`、`list_fullscreen` 等状态驱动路由 + `st.stop()` + JS 模拟点 Tab，历史多次「Tab 劫持/重置/闪」bug 均源于此。缺路由抽象或状态机文档。
3. **Tab 用索引硬编码（低）** — `app.py` 的 JS 用 `idx===0`/`idx===5` 判物品/容器 Tab，Tab 顺序一改就错位。
4. **动态 SQL 复杂化（低）** — `get_filtered_data` 手拼 WHERE + 手排参数，字段一多易错。

## 2. 第三方评审要点（`docs/wms-review.md`）

- **评级 B+**，主矛盾在「分析型需求缺三个一等字段」与「App 层缺处置维度看板」。
- **做得好的**（与独立评审高度重合）：层级定位树、定位覆盖率 3064/3067、外键引用完整性、标签归一化、图片内容寻址去重、`VACUUM INTO` 备份、迁移可重入、采购可追溯、开发流程纪律。
- **真缺口**（按「挖价值+定位」优先级）：
  1. 无「成色/处置」一等字段（`condition`/`disposition`）；
  2. 维护靠标签而非日期（`next_maintenance`，电池类会翻车）；
  3. 无移动流水 `movements`；
  4. 物品命名无管控（无 `category` / Item Master）；
  5. 估值完整性（2500/3067 未计价）+ 缺 `purchase_price` / `resale_value` 区分；
  6. 缺处置维度分流看板；
  7. 缺条码/二维码；
  8. `items.tags` 死字段。
- **落地建议**：三字段幂等迁移 + repo/CSV 透传 + 表单/详情/列表列 + 处置看板 + 测试；并已自纠「价值看板已存在」的半句口误。

## 4. 建议优先级（仅供后续定义 TODO 参考，非承诺）

1. **事务回滚**（应用层 bug，最便宜、风险最低）
2. **三字段 `condition`/`disposition`/`next_maintenance` + 处置看板**（第三方主线，对「挖价值」价值最高）
3. **金额/日期类型治理**（`price` 改整分、日期统一 ISO + 校验）——宜与 #2 同批，否则报表基础不牢
4. **容器环检测 + 图片模型统一 + 加时间戳**（中）
5. 死代码清理、索引、条码（低/收尾）

> 用户决定后续是否立项、如何拆步；本文不展开实现细节。
